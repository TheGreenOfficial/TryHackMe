android apps are mostly written in java or kotlin, compiled to normal java bytecode first then converted into dex bytecode, which runs on dalvik (or art on newer versions, which is the aot/jit successor to dalvik) instead of a regular jvm. an apk is just a zip file, unzip it and you get classes.dex (or multiple dex files if the app is big), res/, assets/, AndroidManifest.xml in binary form, resources.arsc, META-INF/ with the signing certs, and lib/ if the app has native code. apkm/apks/xapk are just split-apk containers some stores use, base apk + config splits for abi/language/density, extract them and youre back to normal apks.

native code comes in through jni, c/c++ gets compiled per architecture into .so files under lib/arm64-v8a, lib/armeabi-v7a etc and gets called from the java/kotlin side. thats usually where the heavier crypto/anti-tamper logic sits since its harder to reverse than plain dex.

workflow: pull the apk with adb, decompile with jadx/jd-gui for java, unpack with apktool for smali/resources and rebuilding, dex2jar/d2j for moving between dex/jar/smali. static analysis is manifest, permissions, exported components, api endpoints, hardcoded secrets, crypto, storage. if its obfuscated (renamed classes/methods, encrypted strings, flattened control flow) you stop trusting names and trace by structure and constants instead.

dynamic analysis after that, frida for hooking methods and bypassing root/emulator checks and ssl pinning, burp for the traffic once pinning is bypassed. .so/jni layer is ghidra/ida territory, jadx and apktool dont touch native code.

same reversing logic applies to .net/c# binaries too, dnspy/dnlib do to clr/il what jadx/apktool do to dalvik/dex, decompile, patch, rebuild.
