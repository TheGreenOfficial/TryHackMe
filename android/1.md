My Conclusion

starting a little from back - android apps are mostly written in Java, or Kotlin, a newer language that fixed a lot of Java's pain points (null safety, less boilerplate, etc) while staying interoperable with it. Whichever one it's written in, it gets compiled to normal Java bytecode first, then converted into dex bytecode, which runs on Dalvik (or ART on newer versions, which is the AOT/JIT successor to Dalvik — Android's equivalent of a JVM for APKs). Btw an APK is just a zip file, unzip it and you get classes.dex (or multiple dex files if the app is big), res/, assets/, AndroidManifest.xml in binary form, resources.arsc, META-INF/ with the signing certs, and lib/ if the app has native code.And for info APKM/APKS/XAPK are just split-APK containers some stores use, base APK plus config splits for ABI/language/density, extract them and you're back to normal APKs.

Workflow according to this lab: pull the APK with adb, decompile with JADX/JD-GUI for Java, unpack with APKTool for Smali/resources and rebuilding, dex2jar/d2j for moving between dex/jar/Smali. It taught static analysis — watch the manifest, permissions, exported components, API endpoints, hardcoded secrets, crypto, storage. If it's obfuscated (renamed classes/methods, encrypted strings, flattened control flow) you stop trusting names and trace by structure and constants instead.

Dynamic analysis after that - even though not directly covered in this room, Frida & Obsidian are the tools for hooking methods and bypassing root/emulator checks and SSL pinning, and Burp for the HTTP traffic analysis. Frida hooks into the app's running process and lets you intercept or overwrite function calls at runtime, so instead of guessing what a check does from static code you can just watch or change what it returns live, which is how root detection and pinning checks usually get bypassed. Burp then sits as a proxy between the device and the server so you can see the actual requests/responses once traffic isn't pinned anymore.
